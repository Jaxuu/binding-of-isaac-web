# ADR-005 · 地牢生成：随机游走邻居生长 + 6 条可测试不变量

- **状态**：已采纳（Accepted）
- **日期**：2025-09-27
- **决策者**：程基岩（技术总监）
- **关联需求**：用户需求 #3（每层 5–8 个房间、房间有门连接、含 1 个 Boss 房）；GDD 01-dungeon；ADR-003（可复现随机）

---

## 1. 上下文（Context）

用户对地牢的硬性要求很具体：

> 随机地牢生成：每层 5-8 个房间，房间之间有门连接，每层有若干房间 + 1 个 Boss 房。

同时 GDD 01-dungeon 要求「Boss 房在最深处」「宝箱房在死路」「所有房间可达」，且任务书要求**每步自测**——这意味着地牢的「正确性」必须能**被自动化断言**，而不是「看起来还行」。

以撒原作的地牢特征是：**房间格阵列**（非连续空间）、**四向门**、**连通图**、**Boss 房最深**、**存在死路**。

## 2. 备选方案（Alternatives）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 随机游走邻居生长 + BFS 定深（选中）** | 天然连通（每个新房都接已有房）；房间数可控；实现短；易断言 | 形状偏「树状」，非循环图 | ✅ **采纳** |
| B. BSP 空间分割 | 房间大小/布局规整 | 为「连续空间地牢」设计；本作是格状房间，BSP 的递归切分用不上，且要额外做房间连接 | ❌ 范式错配 |
| C. 预定义房间模板 + 随机挑选 | 手感可控 | 需大量模板（0 素材约束下要手写），且「随机感」受限 | ❌ 迭代成本高 |
| D. 随机游走 + 删除环边 | 图更「有机」 | 破坏连通性风险高（要额外校验修复），复杂度陡增 | ❌ 收益 < 风险 |
| E. Delaunay/最小生成树 + 补边 | 数学优雅、无死角 | 实现重、坐标非整数格、与「四向门」美术不好对齐 | ❌ 过度工程 |

## 3. 决定（Decision）

**采用方案 A**（`src/systems/dungeon.js`）。

### 3.1 算法流程
1. **定房间数**：`target = rng.int(minRooms, maxRooms)` = `[5,8]`。
2. **起点房**：格坐标 `(0,0)`，`kind = START`。
3. **邻居生长**：维护 `frontier`（前沿房列表）。循环直到房间数达 `target`：
   - `pickFrontier`：从前沿里挑一个**仍有空闲邻格**的房间；60% 偏向「较深」的（形成走廊感），40% 纯随机（形成分支）。
   - `tryExtend`：随机选一个未被占用的方向，新建邻居房 `depth = source.depth + 1`，并在两房间上**双向**标记门。
   - 坐标限制 `|gx| ≤ 6, |gy| ≤ 4`（保证小地图可读）。
   - 死亡前沿（四周被占）从 `frontier` 移除；`frontier` 空则从已有房间重播。
4. **起点保底**：`ensureStartConnections` —— 若起点门数 < 2 且不超 `maxRooms`，硬塞新邻房（避免开局即死路）。
5. **数量兜底**：`topUp` 循环 —— 极端种子下若仍 < `minRooms`，从任意有空位的房间继续扩张。
6. **关键修正**：所有扩容完成后，**重新取 `rooms` 快照**（`Array.from(byKey.values())`）。早期 bug：在扩容前取快照，导致新房间不在列表里，`I5` 断言失败。
7. **BFS 定深**：`computeDepths` 从起点 BFS，得到每个房间的 `depth`。
8. **Boss 房**：`depth` 最大的房间（`I4`）。
9. **宝箱房**：除去 start/boss 后，优先挑**死路房**（门数 = 1）；无死路则挑其余。宝箱房必有 1 个道具（`wantTreasure`）。
10. **其余**统一标为 `NORMAL`。

### 3.2 六条不变量（`validateDungeon`，测试与运行时共用）
| ID | 不变量 | 校验方式 |
|---|---|---|
| **I1** | 房间数 ∈ [5, 8] | `count` 范围断言 |
| **I2** | 所有房间从起点可达 | 从 start BFS，`seen.size === rooms.length` |
| **I3** | 恰有 1 个 Boss 房 | `kind === BOSS` 的房间数 = 1 |
| **I4** | Boss 房是最深的房间 | `boss.depth === max(depth)` |
| **I5** | 无悬空门（门指向存在的邻居） | 逐门查 `byKey[nk]` 存在 |
| **I6** | 门双向一致 | `r.doors[d].opposite` 亦为 true |

`generateFloor` 在运行时也调用 `validateDungeon`，不变量被破坏会在 console 报错（不崩），形成开发期自检。

## 4. 后果（Consequences）

### 正面
- **强连通保证**：每个新房都通过门接入已有房 → 数学上必然连通（`I2` 天然成立，`validateDungeon` 仍会兜底校验）。
- **可复现**：`generateDungeon(seed)` 在 Node 与浏览器完全一致。
- **房间数硬可控**：`I1` 由 `target` + `maxRooms` 上限双重保证。
- **Boss 房位置可预期**：永远最深，符合「越走越深」的叙事。

### 负面 / 代价
- 生成的是**树状图**（无环），少了原作偶尔出现的「环形捷径」。对第一版可接受。
- 死路房不一定存在（宝箱房退化为「非死路房」），属已知取舍。
- `ensureStartConnections` / `topUp` 两个补丁逻辑增加了 `I1` 与 `I5` 之间的耦合风险（曾经的 bug 来源）。

### 缓解
- 500 种子回归测试作为守门（见 §5）。
- 把「取快照时机」写成显式注释（`dungeon.js` 第 118 行），并保留 `maxRooms` 硬上限。

## 5. 验证方式（Verification）

- **Node 单测**：500 个种子全部通过 `validateDungeon`（I1–I6），**0 失败**；房间数范围实测 `[5,8]`。
- **浏览器内 60 种子**（`tests/harness.mjs dungeon`）：
  ```json
  { "bad": 0, "countMin": 5, "countMax": 8 }
  ```
  样例：seed=1 → 8 房 / Boss 深度 5 = 最大深度；seed=2 → 7 房 / Boss 深度 3。
- **视觉**：`10-dungeon-minimap.png` 显示小地图房间与连接。
- **回归**：`dungeon.js` 的 `I5` bug（0,0 的 left 门指向不存在的 -1,0）修复后，500 种子 0 失败。
