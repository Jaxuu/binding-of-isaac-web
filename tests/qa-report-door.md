## 2. 验证方法 —— 我如何独立于工程的脚本

**工程脚本 `tests/door-traversal.mjs` 的盲区**：它**直接调用私有方法** `_checkDoors()` / `_clampPlayer()`，并**手工合成速度**（`p.vx = d.dx * speed; p.x += p.vx*dt`）。它绕过了：

1. **Input 层**（真实 `keydown` → 逻辑动作 `moveX/moveY`）；
2. **`GameState._updatePlaying` 的真实每帧顺序**（移动 → 障碍碰撞 → 射击 → 敌人 AI → `_checkDoors` → `_clampPlayer`）；
3. **`requestAnimationFrame` 驱动的固定步循环**（`FIXED_DT = 1/60`）。

因此它证明不了「玩家**真的按键盘**能走过去」——正是用户实际操作的路径。

**我的独立方法（角度完全不同）**：

| 维度 | 工程脚本 | 本独立脚本 |

### §3.1 门洞隧道上界探测（c5）实测明细

> 目的：正常玩法下 `_checkDoors` 会在玩家**刚进入门洞**（如右门 `x > 610.8`）时立即传送，
> 因此玩家永远到不了 clamp 的放宽上界。为直接测量「放宽后的上界到底在哪」，
> 本用例**临时禁用 `_checkDoors`（传送）**（仅页面内存，`prep` 后 `g._checkDoors = ()=>{}`，测完还原），
> 再用真实键盘沿门轴把玩家推进门洞，断言其**不得越过 `doorRects()` 的外沿**。

| 项 | 实测 |
|---|---|
| 用例数 | **26**（4 方向：down 8 / up 8 / left 5 / right 5） |
| 越过外沿（> 外沿）的用例 | **0** |
| 恰好停在外沿（`maxExcursion === outer`）的用例 | **26 / 26** |
| 横向脱离门洞的用例 | **0** |

结论：放宽后的 clamp 上界**精确等于门洞矩形外沿**（右/下 = `r.x+r.w` / `r.y+r.h`；左/上 = `r.x` / `r.y`），
**不多放宽一像素**。c5 = **26/26 通过**。

> **方法学更正（透明披露）**：c5 首版曾把「隧道探测」也套用 c1–c4 的「虚空」判定
> （`越出活动区 && 不在任何 doorRects() 内`）。但本用例**故意**让玩家沿门轴停在门洞外沿，
> 该外沿点恰是「越出活动区且在矩形边界上（严格 `<` 判定视为不在矩形内）」——
> 属**断言语义**问题，**非产品缺陷**（实测越界 0、横向脱离 0）。
> 已把 c5 断言更正为「不越过外沿 + 横向不脱离门洞」，故 26/26 通过。

## 附录 A：测试自身方法学修正（诚实记录）

独立验证过程中，**我发现自己脚本的一处「虚空」判据写错**，并已修正——记录在此以免误导：

- **初版 `voidViolation` 用「玩家中心活动区上界」（`ROOM_W - pad = 607`）当作「房间边界」**。
- 但 `doorRects()` 的右门触发区起点是 `ROOM_W - PLAY_PAD*0.6 = 610.8`，二者之间存在 **3.8px 的门槛间隙（607, 610.8）**——该间隙**仍在房间内容区（0..624）之内**，是**门洞门槛**，不是「虚空」。
- 初版据此把「玩家沿门轴推入时途经门槛」**误报为越界**（c5 假失败：`maxExcursion === outer`，即玩家**恰好止于门洞外沿、从未越出**）。
- **修正**：`voidViolation` 改用**房间内容区真实边界**（`0..ROOM_W` / `0..ROOM_H`）判定「房间边界之外」；c5 改为直接断言 ① **不越过门洞外沿**、② **横向不脱离门洞**。

> 关键实测事实（两次运行一致）：`maxExcursion` **恒等于** `outer`（门洞外沿），**从未超过**——即 clamp 上界正确、无穿墙。
> 本修正**不是**「为让结论好看而降低断言」：修正后的判据在「外沿」维度**更强**（直接卡 `doorRects()` 外沿），只是纠正了对「房间边界」的错误取值。
